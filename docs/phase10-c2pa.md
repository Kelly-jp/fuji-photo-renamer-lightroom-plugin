# Phase 10：書き出し JPEG の C2PA / JUMBF 削除

## 範囲と状態

`0.9.0.21` で「C2PA / Content Credentialsを削除する」を実装しました。既定OFF。ONは今回生成されたJPEGの作業出力だけからJUMBF全体を除去します。C2PA以外のJUMBFも失われ、再署名・外部マニフェスト・RAW等の形式は対象外です。

元RAW/JPG/XMP・カタログ元写真は変更しません。実ExifToolのmacOSテストと許諾済み実JPEGコピーでは削除・保持を確認済みです。macOSのLightroom内では削除・表示保持・前回設定の書き出しが確認報告済みで、Windows実機は未確認です。

## 所有確認と処理

1. SDKの `rendition:type()` / `destinationPath` と、成功した `waitForRender` のパス、`photo:getRawMetadata('path')` を照合する。
2. ExportArtifactが元画像・関連入力と生成JPEGの別名解決後のパスを比較し、JPEG構造・内容のスナップショットを保存する。呼び出し元へ不透明なハンドルを返し、任意パスや偽のテーブルを削除APIへ渡せないようにする。
3. ExifToolが新規作業ディレクトリを確保し、固定名cleaned.jpgへ `-o` と `-jumbf:all=` で出力する。入力は読み取るだけ。既存作業出力を置換しない。
4. source内容の不変、生成コピーの参照先、JPEG構造、JUMBF以外の全バイト列の一致を検証する。
5. ExifToolで `-j -G1 -s -JUMBF:all -Error -Warning` を再実行し、終了コード0・有効なJSON・SourceFile一致・JUMBF/警告/エラーなしを確認する。
6. キャンセルを確認し、元写真への参照とSDK生成JPEGの内容を再確認する。検証済みコピーの保存準備としてSDK生成JPEGだけを削除し、FileSystemで新しい最終名へ非上書き移動する。
7. 所有する既知の作業ファイルだけを清掃する。不明なファイルや停止未確認の作業は保持して理由を報告する。

OFFはPhase 9の転送を維持し、削除コマンドや作業コピー生成は呼びません。削除・検証失敗を成功扱いにせず、最終保存は実行しません。清掃だけの失敗は出力の成功と区別した警告です。保存失敗では原画像が残るため再書き出しできますが、SDK生成JPEGと未確定の処理済みコピーを両方残す保証はしません。

## ExifTool仕様の確認

[公式Jpeg2000/JUMBF資料](https://exiftool.org/TagNames/Jpeg2000.html) はJPEGのJUMBFグループ削除に `-jumbf:all=` を指定しています。[公式CLI資料](https://exiftool.org/exiftool_pod.html) は `-o` の新規出力・既存ファイル拒否と、`-overwrite_original`併用時の入力削除を説明しています。

このためバックアップ抑止のために元ファイル書き換えフラグを加えず、`-o`で処理済みコピーを作る方式を採用しました。通常の_originalバックアップは作りません。既存のmacOS/Windows期限付きrunnerを共用し、各コマンドの既定上限は30秒です。失敗・警告・不正JSONを握りつぶしません。詳細は [ADR 0001](adr/0001-c2pa-private-output.md)。

SDK型・destinationPathは固定SDKのLrExportRendition.html、写真パスはLrPhoto.html、コピー/移動/削除/属性はLrFileUtils.htmlで確認しました。[既存SDK出典](phase1-lightroom.md#参照資料の出典)

## 独立したJPEG検証

core/JpegIntegrityはSDK・ExifTool・I/Oに依存しません。SOI、フレーム、SOS、エントロピー区間、EOI、APP11のJPパケットとjumbボックスを解析し、JUMBFパケットを除いた元バイト列と処理済みJPEG全体を比較します。画像の圧縮データ・テーブル、ICC、EXIF、XMP、対象外APP11、その他の非JUMBF領域が変われば拒否します。

完全なJPEGデコーダーやC2PA署名検証器ではありません。テストでは独立したPillowデコードでも実JPEGの画素一致を確認しました。製品の依存へPillowを追加していません。

現在は各JPEG64 MiBまで、8/12ビットDCT系JPEG、32ビット長のJUMBFボックスと連続したAPP11パケットに限定します。大きいファイル、拡張/不定長JUMBF、未対応構造は切り詰めず拒否します。作業パスの%はExifTool出力書式との誤解釈防止のため拒否します。検証メモリはファイルサイズに比例します。

## 検証と手動手順

合成JUMBFの単一・分割パケット、JUMBF不在、破損、偽ハンドル、元画像参照、処理中の変更、警告、非ゼロ終了、タイムアウト、虚偽の成功、ON/OFFとキャンセルをテストしています。許諾済み実JPEGコピーではJUMBF消失、非JUMBF全バイト一致、Pillowのデコード・画素一致、入力SHA-256不変を確認しました。個人写真やメタデータはコミットしていません。SDK境界はダブルで、Lightroom実機成功とは区別します。

1. プラグインを再読み込みして `0.9.0.21` を確認する。
2. 専用カタログの複製素材と空の保存先を使い、ExifToolを指定する。
3. OFFで書き出し、生成JPEGにContent Credentialsが含まれるか確認する。Lightroomの署名設定によっては元に存在しても出力に含まれないため、プラグインの削除設定と区別する。
4. ONで書き出す。同名は_001等へ進み、書き出し前から存在していた元RAW/JPG/XMPとOFF出力について、同じ絶対パスのファイルのON書き出し前後のSHA-256が変わらないことを確認する。新しく作ったON出力とOFF出力のJPEG同士はJUMBFの有無で内容が異なるため、SHA-256一致を要求しない。
5. 出力を `exiftool -JUMBF:all -Error -Warning output.jpg` で確認し、JUMBFがないこと、JPEG表示・色・画像内容・対象外メタデータが維持されることを確認する。
6. 「前回の設定で書き出し」も確認し、余分な元名JPEGが残らないことを確認する。
7. 不正ツール・権限不足・途中キャンセルで成功扱いにならず、所有外のファイルが削除されないことを確認する。

残課題は元画像の書き出し前後ハッシュ比較、署名の有効性の確認、Windows、別ボリューム・競合・リンクの実機確認、広いJPEG/C2PA構造の検証です。作業コピーの新規生成はExifTool -o契約に依存し、任意のハードリンク構造をSDKで識別できたと主張しません。Phase 11には進まず次の指示を待ちます。

## 手動確認報告とハッシュ比較の整理（2026-10-11）

ユーザーがJUMBF消失、JPEG表示・色・画像内容・対象外メタデータの維持、前回設定での書き出しを確認しました。SHA-256差分は通常書き出しJPEGとプラグイン書き出しJPEG（衝突回避の_001付き）の比較だったと確認できました。これは別々の出力の比較であり、元RAW/JPG/XMPや既存出力が変更されたという報告ではありません。JUMBF削除により出力バイト列が変わるため、両出力のハッシュ一致は要求しません。今回の実機確認では、既存の同一パスの元RAW/JPG/XMP・OFF出力の前後ハッシュ比較は未実施として残します。

続いて、削除ONの通常操作と「前回と同じ設定」で生成した2出力を読み取り専用で比較しました。両JPEGは同じサイズで、6240×4160のデコード後RGB画素が完全一致し、ExifToolでJUMBFは両方とも未検出でした。JPEGセグメントの差分はEXIFとXMPのAPP1だけで、圧縮画像データ・その他セグメントはバイト一致しました。メタデータ差分は更新日時・メタデータ日時・履歴日時・DocumentID/InstanceID（履歴分を含む）です。別々のレンダリングで出力に記録された日時と識別子の差がSHA-256不一致の原因であり、今回の比較に処理変更は不要です。比較前後の両入力バイト列も不変でした。個人のファイルパスや識別子は記録しません。

ユーザーのWindows実機がないため、Windowsの手動検証は環境確保まで保留します。macOSでの確認をもってPhase 10を区切り、Windows実機動作は未検証として扱います。

# Phase 9：書き出しパイプライン統合

## 実装と状態

バージョン `0.8.3.20`。Phase 1 の固定 `test_` 命名を終え、書き出し画面のテンプレートで実際の JPEG を保存します。対応トークンは 9 個で、Extension / ISO / FocalLength / Sequence は廃止済み。拡張子はレンダリング結果から自動付加します。Lightroom 内の今回の経路はまだ手動確認していません。

ルート `ExportServiceProvider.lua` は SDK 登録用の入口と依存の接続だけを担当し、処理を `lightroom/ExportServiceProvider.lua` へ移しました。`infrastructure/MetadataReader.lua` は探索・読取・項目統合を接続し、`FileSystem.lua` は標準保存先・サブフォルダーと非上書きコピーを担当します。core へ SDK / ExifTool / ファイル I/O を追加していません。

## 書き出しの流れ

1. UI 設定と標準保存先をセッション用の新しいテーブルへ固定する。テンプレートと ExifTool の所在、C2PA OFF を確認する。
2. Lightroom の一時 JPEG を `waitForRender()` で取得し、キャンセル・生成結果・形式を検証する。
3. 各 rendition の `photo:getRawMetadata('path')` から元パスを取得し、読み取り可能な実ファイルを確認する。
4. MetadataSourceResolver で XMP / RAW / JPG を探索する。各入力を ExifTool で読み、MetadataResolver が項目ごとに XMP → RAW → JPG の順で採用する。
5. TemplateParser / TokenResolver が元名・同一メーカー省略を展開し、FilenameSanitizer が候補を整形する。
6. FileSystem が保存先を解決し、明示されたサブフォルダーだけを必要時に作る。元画像・関連入力とレンダリング済みファイルの別名解決後のパスを比較する。
7. CollisionResolver が候補を生成し、各候補を実保存先で確認する。既存ファイル・ディレクトリは `_001` / `_002` へ進む。SDK の `copy` で新しいファイルだけを保存する。
8. 成功・失敗・警告を報告する。失敗は `uploadFailed`、キャンセル後は新規保存しない。一時レンダリングの清掃は Lightroom に任せ、元 RAW / JPG / XMP や不明な部分ファイルを削除しない。

通常の名前に連番は付けません。同名がある場合だけ衝突回避番号を付けます。旧プリセット末尾の Sequence は UI で移行し、それ以外の位置では修正を促すエラーとします。

C2PA ON は引き続き拒否します。削除処理は Phase 10 まで実装しません。OFF ではレンダリング結果をそのままコピーするため、この段階では別の作業コピーを作りません。ON の作業コピー・所有追跡は Phase 10 の検証で追加します。

## ExifTool 設定と実写真プレビュー

プリセット対象へ `fprExifToolPath`（既定空文字）を追加しました。「ExifTool 実行ファイルを選択…」で検証用ツールの絶対パスを選びます。空なら既存の同梱パスへ解決し、PATH へのフォールバックはしません。配布ペイロードは未準備で、開発時はツールの明示指定が必要です。今回の自動検証は ExifTool 13.55 です。

初期プレビューはサンプルです。「選択中の写真でプレビューを更新」は `LrApplication.activeCatalog():getTargetPhoto()` の写真から、同じ MetadataReader を非同期に呼びます。これはカタログの選択写真であり、書き出し対象の先頭と同一とは保証しません。写真を変えたらボタンで再取得してください。実書き出しは各 rendition の元画像から読み直します。

テンプレート・メーカー設定は取得済み項目で即時更新します。RAW モード・ExifTool パス変更時は取得結果を無効にし、サンプルへ戻します。設定変更・画面終了・新しい取得要求後に到着した古い結果は破棄します。未選択・取得失敗はサンプルであることと理由を表示します。実写真の日時欠落をサンプル日時で埋めません。ExifTool の警告も表示します。衝突名は未確定です。

## 保存境界と設計の具体化

core の比較キーは既知の試行名・予約名を扱う完全一致で使い、実候補すべてに `LrFileUtils.exists` を呼びます。大小文字・Unicode 等価性を Lua で推測せず、OS / SDK の保存先確認へ委ねる方式です。確定済み名もセッションで記録します。さらに `copy` の既存保存先拒否契約を使い、存在確認だけを非上書き保証としません。実 OS / SDK での競合・リンク・等価性検証は未完了です。

**コピー開始後の失敗は再試行しません。** 初期設計では保存時衝突の再解決を想定しましたが、SDK のコピー失敗から「他プロセスの新規ファイル」と「自分の部分コピー」を安全に識別できません。成功へ進むと不完全な副産物を隠すため、原因と保存先を報告してその写真を失敗にします。既存候補の衝突は従来の要件どおり別名化します。不明な部分ファイルは所有を推測して削除しません。

成分長・フルパス長は未実測です。名前を切り詰めず、SDK の存在確認・コピーで例外や失敗になれば失敗として通知します。任意の 255 文字 / 260 文字制限を推測で適用しません。元画像とレンダリング結果のパス比較は別名解決と保守的な大小文字比較に限定し、ハードリンク等の実体同一性は保証済みとしません。

カタログへの追加・スタック追加は引き続き適用しません。終了ダイアログは現在の検証用件数報告として維持しています。

## SDK の根拠

既存の [Phase 1 SDK 出典](phase1-lightroom.md#参照資料の出典) と [Phase 8 の固定スナップショット](phase8-export-dialog.md#sdk-確認資料と-api) の Adobe 作成 API Reference を使用しました。コピー契約は LrFileUtils.html の copy / exists / resolveAllAliases、選択写真は LrApplication.html の activeCatalog と LrCatalog.html の getTargetPhoto を照合しています。startAsyncTask / pcall は LrTasks.html、元パス・レンダリング・通知は既存 Phase 1 の API です。存在しない API、カーソル位置取得、元画像変更 API は追加していません。ミラーの公式 ZIP との同一性は未確認のままです。

## macOS 手動検証

1. プラグインを再読み込みし、`0.8.3.20` を確認して書き出し画面を開き直す。専用カタログと複製した RAF / DNG / JPG / XMP、空の検証用保存先を使う。
2. 書き出し先「Fuji Photo Renamer — 開発検証版」を選択し、「ExifTool 実行ファイルを選択…」で検証用ツールを指定する。macOS の既存 Homebrew 環境なら `/opt/homebrew/bin/exiftool`。C2PA 削除は OFF。
3. `{DateTime}_{CameraMaker}_{Camera}_{LensMaker}_{Lens}_{FilmSim}_{Original}` を入力する。「選択中の写真でプレビューを更新」で実写真の候補と省略を確認する。写真選択と書き出し対象が違う場合はプレビューを確定名と扱わない。
4. RAW の3モード、メーカー省略 ON/OFF、特定フォルダー / 元フォルダー＋サブフォルダーを切り替えて書き出す。テンプレートの候補に従う名前、実際の `.jpg` / `.jpeg`、画像の表示を確認する。
5. 同じテンプレートで再度書き出し、既存出力が不変で `_001`、続けて `_002` が生成されることを確認する。番号なし → _001 → _002 となり、番号が二重にならないことを確認する。
6. 複数枚・同じ stem・日時欠落・元画像不在・不正 ExifTool パス・書き込み権限不足・途中キャンセルを確認する。失敗を成功と表示せず、失敗した写真を理由に正常な出力へ番号を付けないことを確認する。
7. 同梱ツールがない環境でパスを空にし、明示的に失敗することを確認する。C2PA ON でも書き出しが止まることを確認する。
8. 元 RAW / JPG / XMP と既存出力の SHA-256 を前後比較する。元の Lightroom カタログ画像が移動・変更されていないことを確認する。

Lightroom の現像変更がカタログ内にしかなく、ファイルの XMP / DNG / JPG へ保存されていない場合、その設定は今回の読取では取得しません。撮影時 RAF と編集後の FilmSim の違いは既存の採用元診断でも確認してください。

## 前回の設定による二重出力への対処（2026-10-10）

ユーザーから「前回の設定で書き出し」で元名の JPEG とテンプレート名の JPEG が残る報告を受けました。匿名化した例は original.jpg と FUJIFILM_X-H2S_original.jpg です。名前の組み合わせから、SDK のレンダリング結果が最終フォルダーへ生成され、プラグインのコピーが別ファイルを追加した経路と判断しました。Lightroom 内の保存先切り替え・キャッシュの詳細は未確定で、過去の SDK 不具合報告だけで現在の原因を断定しません。

今回の確定保存は、入力群と別ファイルであることを検証した SDK 生成 JPEG に対して LrFileUtils.move を使います。コピーではないため、転送成功時に元名の SDK 出力を残しません。最終名と生成済みパスが完全一致する場合は、その生成ファイルを完成品として扱い、余計な衝突番号を付けません。既存の別ファイルは衝突回避し、SDK の既存保存先拒否契約を併用します。

元 RAW / 元 JPG / XMP は移動対象にしません。レンダリング結果と元画像の同一性を読取前にも確認し、入力探索で発見された今回の SDK 生成 JPEG をメタデータ源から除外します。これにより、元 RAW と同階層へ生成された JPEG を元 JPG と取り違えません。

updateExportSettings が一時設定へ再適用されても、退避した最終保存先を tempFolder で上書きしないようにしました。復元情報がない場合は推測で保存せず、書き出し画面から保存先を指定し直すようエラーにします。

move の仕様は固定 SDK の Adobe 作成 LrFileUtils.html を照合済みです。SDK 1.3 以降対応、移動先の親が必要、既存保存先があると失敗し、成功時 true / 失敗時 false と理由を返します。移動失敗や不明な部分出力は削除・再試行しません。過去のコピー前提の記録は履歴であり、現行はこの転送方式です。

0.8.3.20 を再読み込みし、空の検証用フォルダーを通常の書き出し画面で指定して1枚出力後、1枚だけ選択して「前回の設定で書き出し」を実行してください。追加されるファイルがテンプレート名の _001 だけで、元名 JPEG が増えないことを確認します。元 RAW / JPG / XMP のハッシュも確認します。過去に作られたファイルは自動削除しません。今回の Lightroom 実機経路・移動の競合・異なるボリューム間転送の確認は未実施です。
